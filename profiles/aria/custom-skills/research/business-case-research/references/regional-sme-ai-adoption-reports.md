# Regional SME AI Adoption Reports

Use this pattern when the audience accepts that AI matters but cannot identify a first use case. The report must convert abstract interest into a scoped, measurable pilot rather than merely showcase impressive companies.

## Decision Frame

Start from business loss, not model capability:

1. Repetition: recurring report, data entry, or form work.
2. Delay: slow search, diagnosis, quotation, response, or scheduling.
3. Quality: defect escape, inconsistent inspection, scrap, or rework.
4. Downtime: reactive maintenance and unplanned stoppage.
5. Concentration risk: decisions or know-how held by one expert.

Write the core question as: **Which loss will be reduced, with which data, measured by which KPI, under whose approval?**

## Required Structure

1. Regional/industry context from an official source.
2. “What work can AI do?” map: field complaint → workflow → minimum data → first KPI → difficulty.
3. Evidence-graded case table: adopter, before/after workflow, disclosed result, evidence class, transferable lesson.
4. Adoption ladder ordered by data readiness:
   - document drafting/search and inquiry triage;
   - diagnosis and quotation support;
   - visual inspection;
   - predictive maintenance and process optimization.
5. Three to five pilots with duration, inputs, KPI, human approval, and stop criteria.
6. A 90-day plan with decision gates, not a guaranteed rollout.
7. Sales/education conversion: audience promise, session outputs, consultation questions, and usable campaign copy.
8. Evidence limits and security controls.

## Case Selection

- Balance core operations with adjacent functions such as technical sales, customer response, internal knowledge, and reporting.
- Prefer cases that reveal workflow and measured change. Large enterprises are acceptable only when the report explicitly extracts a small-team practice rather than copying absolute savings.
- Use separate rows for materially different workflows from the same adopter, but do not misstate them as independent companies.
- Treat vendor customer stories as possibility evidence, not guaranteed or audited ROI.

## Pilot Design

Each pilot must name:

- one workflow and one owner;
- minimum viable data and permissions;
- baseline and target KPI;
- human approval point;
- stop criteria for accuracy, stale sources, false alarms, or uncontrolled operating conditions;
- scale, revise, or stop decision at the end.

Start with read → recommend → approve → execute. Do not begin with automatic sending, pricing, scheduling, quality disposition, safety action, or equipment control.

## Persuasion Pattern

Avoid: “We teach AI tools.”

Prefer: “We identify one costly workflow, verify whether its data is usable, and leave you with a 90-day pilot and measurement plan.”

Useful consultation prompts:

- Which repeated task consumes the most hours each week?
- Which defect, rework, or stoppage costs the most?
- Which decision depends on a single expert?
- Which answer requires searching across multiple files or systems?
- What one number should improve within 90 days?

## Verification

- Count case rows programmatically and compare with the promised count.
- Check that every case row has an inline citation and evidence label; prose citation coverage tools may exclude tables.
- Confirm every quantitative claim preserves source qualifiers such as estimated, potential, pilot, or simulation.
- Verify the HTML has no duplicate IDs or broken source anchors and includes print/mobile styles.
- If visual rendering is unavailable, report static verification only; do not claim visual QA.
